# STALKER PDA Workflow

## Правила для AI-асистента

**ОБОВ'ЯЗКОВО дотримуватись цього порядку. Пропускати кроки ЗАБОРОНЕНО.**

### ⚠️ КРИТИЧНЕ ПРАВИЛО: САМОПЕРЕВІРКА

**Після КОЖНОГО кроку AI ОБОВ'ЯЗКОВО:**
1. Перечитати цю інструкцію
2. Звірити виконаний крок з описом
3. Визначити наступний крок
4. Переконатися, що нічого не пропущено

```
🔍 САМОПЕРЕВІРКА після кроку X.X:
- Виконано: [що зроблено]
- Наступний крок: X.X — [назва]
- Пропущено: нічого / [що пропущено]
```

### ⚠️ КОНТРОЛЬ ВІДХИЛЕНЬ (Alignment Check)

**Після КОЖНОЇ дії ОБОВ'ЯЗКОВО перевірити:**

1. **Що зроблено vs що планувалось**
2. **Звірка з потребою (README.md)**
3. **Консистентність документів**
4. **Перевірка коду (якщо є)**

**Якщо знайдено розбіжність → STOP → Зафіксувати → Обговорити**

## АЛГОРИТМ РОБОТИ З НОВОЮ ПОТРЕБОЮ (8 етапів)

```
┌─────────────────────────────────────────────────────────────────────────────┐
│  REQUIREMENTS PHASE (Working Backwards)                                      │
├─────────────────────────────────────────────────────────────────────────────┤
│   1. DRAFT          → Проблема + Прес-реліз                                 │
│   2. ANALYSIS       → Питання + Відповіді                                   │
│   3. SPEC           → Acceptance Criteria + 10 розділів                     │
│   4. ДОКУМЕНТАЦІЯ   → Всі файли в docs/needs/NEED-XXX/                      │
├─────────────────────────────────────────────────────────────────────────────┤
│  IMPLEMENTATION PHASE                                                        │
├─────────────────────────────────────────────────────────────────────────────┤
│   5. PRE-CHECK      → Checklist перед кодом                                 │
│   6. КОД + ТЕСТИ    → Backend → Frontend → Tests → Звіт                     │
│   7. GIT COMMIT     → Після апруву                                          │
├─────────────────────────────────────────────────────────────────────────────┤
│  FINALIZATION PHASE                                                          │
├─────────────────────────────────────────────────────────────────────────────┤
│   8. ЗАВЕРШЕННЯ     → Оновлення docs + Фінальна перевірка                   │
└─────────────────────────────────────────────────────────────────────────────┘

⚠️ ВАЖЛИВО: На КОЖНОМУ етапі звіряємось з README.md потреби!
```

### ЕТАП 1: DRAFT (Чернетка)

**Крок 1.1** — Визначити номер NEED
- Перевірити `docs/needs/INDEX.md` для визначення наступного номера

**Крок 1.2** — Описати проблему
- Що не працює / чого не вистачає?
- Кого це стосується?

**Крок 1.3** — Написати прес-реліз (Working Backwards)
- Уявити, що фіча вже готова
- Написати 2-3 речення як анонс для користувачів

**Крок 1.4** — Запит апруву Draft
```
📋 АПРУВ DRAFT

Потреба: NEED-XXX — Назва
Проблема: [опис]
Прес-реліз: [текст]

Підтверджуєш перехід до Analysis?
```

---

### ЕТАП 2: ANALYSIS (Розширений аналіз)

#### Крок 2.1 — Discovery питання (5 yes/no)

Задати ПО ОДНОМУ з дефолтом.

```
Q1: Чи буде взаємодія через UI (PDA/Admin)?
    [Default: Yes]

Q2: Чи потрібна авторизація (JWT)?
    [Default: No — якщо не працюємо з персональними даними]

Q3: Чи змінюється існуючий API (endpoints)?
    [Default: No — краще додавати нові]

Q4: Чи потрібні зміни в базі даних (MySQL)?
    [Default: No]

Q5: Чи є схожий функціонал в системі який можна взяти за основу?
    [Default: Yes — перевірити docs/needs/INDEX.md]
```

#### Крок 2.2 — Автономний аналіз коду (AI виконує сам)

**БЕЗ питань до користувача** AI аналізує:
- Схожі реалізовані фічі
- Файли які потрібно змінити
- Патерни та конвенції проекту
- Потенційні конфлікти

#### Крок 2.3 — Expert питання (5 технічних yes/no)

На основі аналізу коду — конкретні технічні питання.

#### Крок 2.4 — Підсумок Analysis

```
📋 ПІДСУМОК ANALYSIS

Discovery відповіді: [список]
Аналіз коду: [результат]
Expert відповіді: [список]

Підтверджуєш перехід до Spec?
```

---

**Крок 3.2** — Проробити всі розділи специфікації (0-10)

### ЕТАП 4: ДОКУМЕНТАЦІЯ

### ЕТАП 5: PRE-IMPLEMENTATION CHECK

**Крок 5.1** — Проаналізувати поточний код
**Крок 5.2** — Pre-implementation Checklist

```
📋 PRE-IMPLEMENTATION CHECKLIST

✅ План дій:
- [ ] Прочитав tasks.md
- [ ] Зрозуміло що саме потрібно реалізувати
- [ ] Знаю в якому порядку робити

✅ Файли:
- [ ] Файли які потрібно EDIT — існують
- [ ] Розумію де створювати NEW файли

✅ Відповідність документації:
- [ ] Звірив з spec.md
- [ ] Звірив з errors.md
- [ ] Звірив з README.md (вихідна потреба)

✅ Acceptance Criteria:
- [ ] Критерії зрозумілі та реалістичні
```

**Крок 5.3** — Описати план змін та запросити апрув

### ЕТАП 6: НАПИСАННЯ КОДУ

**Крок 6.1** — Після апруву написати код (Backend First)

2. Frontend — React компоненти, сторінки

**Крок 6.2** — Manual testing

## ЗАБОРОНЕНО

- ❌ Пропонувати код без готової документації
- ❌ Об'єднувати апрув документації і коду в один запит
- ❌ Пропускати Analysis якщо є хоч одне питання
- ❌ Починати код до апруву специфікації
- ❌ Переходити до наступного етапу без явного апруву
- ❌ Задавати кілька питань одночасно в Analysis

## QUICKFIX (Швидкі фікси)

Для багів і дрібних виправлень (без повного циклу):

**Коли можна використовувати:**
- Виправлення тексту/помилок
- Зміна конфігурації
- Мінорні баги

**Процес:**
1. Описати проблему і рішення
2. Запит апруву
3. Після апруву — виконати
4. Створити `docs/needs/QUICKFIX-XXX-назва/README.md`

## Правила коду

### Формат запиту на зміни (PROPOSE CHANGE)

```
[PROPOSE CHANGE]

Ціль: <що і навіщо>
Файли: <список>
Підхід: <алгоритм>
Ризики: <що може зламатися>

❓ Прошу апрув
```

### Рефакторинг

**Рефакторимо ТІЛЬКИ якщо:**
- ✅ Блокує нову фічу
- ✅ Критичні проблеми (security, memory leaks)

**НЕ рефакторимо:**
- ❌ Код який працює і не заважає
- ❌ "Попутні покращення"

### Коміти
Формат: `[NEED-XXX] опис` або `[QUICKFIX-XXX] опис`

## Статуси потреб

| Статус | Опис |
|--------|------|
| `draft` | Чернетка |
| `analysis` | Аналіз/проробка |
| `spec` | Специфікація готова |
| `in-progress` | В розробці |
| `done` | Завершено |
